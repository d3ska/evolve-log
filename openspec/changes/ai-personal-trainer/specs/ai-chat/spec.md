## ADDED Requirements

### Requirement: Streaming chat endpoint
The system SHALL expose `POST /api/ai/chat` that accepts `Content-Type: application/json` and returns `Content-Type: text/event-stream`. The request body SHALL contain `message` (String, required), `conversationId` (UUID, nullable), and `pageContext` (String, nullable — one of `dashboard`, `workouts`, `progress`, `blood`). The endpoint SHALL be authenticated.

#### Scenario: SSE stream opened on valid request
- **WHEN** an authenticated user posts a valid chat message to `/api/ai/chat`
- **THEN** the response immediately returns HTTP 200 with `Content-Type: text/event-stream` and begins emitting SSE events

#### Scenario: Missing API key returns error event
- **WHEN** an authenticated user posts to `/api/ai/chat` but has no API key configured in `ai_settings`
- **THEN** the stream emits a single `error` event with message `"No API key configured. Please add your API key in Settings."` and closes

### Requirement: Typed SSE event protocol
The system SHALL emit typed SSE events using the `event:` field. The protocol SHALL define exactly five event types: `token`, `tool_use`, `tool_result`, `done`, and `error`. Each event's `data:` field SHALL be a JSON object.

#### Scenario: token event carries text chunk
- **WHEN** the AI streams a text token
- **THEN** the emitted SSE event has `event: token` and `data: {"text": "<chunk>"}` where `<chunk>` is the incremental text

#### Scenario: tool_use event emitted before execution
- **WHEN** the AI requests a tool
- **THEN** the emitted SSE event has `event: tool_use` and `data: {"tool": "<name>", "label": "<human-readable message>"}` emitted before the tool executes

#### Scenario: tool_result event emitted after execution
- **WHEN** a tool finishes executing
- **THEN** the emitted SSE event has `event: tool_result` and `data: {"tool": "<name>", "rowCount": <n>}`

#### Scenario: done event closes stream
- **WHEN** the AI response is complete and the full message is persisted
- **THEN** the emitted SSE event has `event: done` and `data: {}` and the `SseEmitter` is completed

#### Scenario: error event on provider failure
- **WHEN** the AI provider returns a non-2xx response or throws an exception
- **THEN** the emitted SSE event has `event: error` and `data: {"message": "<user-safe error description>"}` and the stream is closed

### Requirement: DB-persisted conversation history
The system SHALL persist every chat message (both user and assistant turns) to the `ai_chat_history` table with columns `user_id`, `conversation_id`, `role` (user | assistant), `content`, and `created_at`. The assistant message SHALL be persisted after the stream completes (on `onDone()` callback).

#### Scenario: User message persisted on request
- **WHEN** a chat request arrives
- **THEN** the user's message is saved to `ai_chat_history` before the AI call begins

#### Scenario: Assistant message persisted after stream
- **WHEN** the SSE stream completes (done event fired)
- **THEN** the full assistant response text is saved to `ai_chat_history` with `role = 'assistant'`

#### Scenario: History survives server restart
- **WHEN** the server restarts and a returning user sends a message with the same `conversationId`
- **THEN** the last 10 messages from that conversation are retrieved from `ai_chat_history` and included in the AI context

### Requirement: Last 10 messages injected as context
The system SHALL fetch at most 10 most recent messages for the given `conversation_id` from `ai_chat_history`, ordered by `created_at DESC`, then reverse them to chronological order before prepending to the `AiRequest` messages list.

#### Scenario: Context limited to 10 messages
- **WHEN** a conversation has 15 stored messages and a new message arrives
- **THEN** only the 10 most recent prior messages are included in the AI request (not all 15)

### Requirement: Page context injection
The system SHALL map the `pageContext` field to a pre-fetched data snapshot injected into the system prompt. The mapping SHALL be: `dashboard` → last 7 days session count + volume by muscle + PRs; `workouts` → last 5 workout sessions with exercises; `progress` → last 4 weeks volume + progressive overload for top 3 exercises; `blood` → most recent blood test results; `null` → user profile only.

#### Scenario: Progress page context injected
- **WHEN** a chat message arrives with `pageContext: "progress"`
- **THEN** the system prompt includes last 4 weeks volume and progressive overload data computed from SQL, not from the AI model

#### Scenario: Null context sends minimal profile
- **WHEN** a chat message arrives with `pageContext: null`
- **THEN** the system prompt includes only the user's name and any configured goals, with no training data block

### Requirement: Conversation ID generated by frontend
The system SHALL accept `conversationId` as a UUID supplied by the client. If `conversationId` is null on the first message, the frontend SHALL generate a new UUID (v4) and include it on all subsequent messages. The backend SHALL store the provided `conversationId` in `ai_chat_history` without generating it server-side.

#### Scenario: New conversation assigned an ID by client
- **WHEN** the frontend sends a first message with no prior `conversationId`
- **THEN** the frontend generates a UUID, sends it in the request, and the backend stores it verbatim in `ai_chat_history`

### Requirement: SseEmitter timeout
The system SHALL configure `SseEmitter` with a 60-second timeout. If the timeout is reached before the stream completes, the emitter SHALL be completed with an `error` event containing a timeout message.

#### Scenario: 60-second timeout closes connection
- **WHEN** 60 seconds elapse without the stream completing
- **THEN** the `SseEmitter` completes and the client receives an `error` event with a timeout message
